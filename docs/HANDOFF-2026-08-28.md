## 4. 遗留问题（核心）：第二条及以后的 TLS 连接必然失败

### 现象（每次启动 100% 复现，与网络无关）

- 自测流程 `boot_network_self_test()`（`main/main.cpp:331`）：HTTP 建 session → WSS kind=0（转写）→ WSS kind=1（问答）
- **HTTP 永远成功**（约 7-20 秒，status=200）
- **两个 WSS 永远失败**：握手停在不同阶段（有次卡在读证书中段 65 秒，有次等 server hello 就没了下文），最后报 `tls_error_code=10368`（= X509_ALLOC_FAILED -0x2880）或 `-0x0010`（MPI_ALLOC），或 connect timeout `bits=0x0/0x2`

### 关键证据（决定性的一条）

`clare_sw_sha_20260828.log` / `clare_zky_test_20260828.log` 中的堆水位对比：

```
HTTP before init:  free8=42808 largest8=25088
HTTP after cleanup: free8=36620 largest8=14592   ← 一次 HTTP 会话后永久丢失 ~6KB，且最大连续块掉 10KB
WS pre-start:      free8=39156 largest8=14592
WS ERR heap:       free8=28752 largest8=14592     ← 之后证书解析触发 X509_ALLOC
```

结论：**esp_http_client / esp-tls 的清理路径泄漏约 6KB + 碎片化**，WSS 握手需要大块连续内存做证书解析，于是失败。之前一度怀疑手机热点蜂窝桥接（65 秒读停顿），但同样失败在 ZKY 办公网复现，网络因素已排除。

## 5. 已知坑清单（每个都实际踩过）

1. **sdkconfig 生成文件"首写优先"**：改了 `sdkconfig.defaults` 或 `sdkconfig.local` 后，必须 `rm -f build/sdkconfig.private` 再 `idf.py reconfigure`，否则新值静默不生效（本会话踩了两次，见 `开发经验.md:264`）。
2. **iPhone 热点名含 Unicode 弯引号**：`oxygen’s iPhone` 里的撇号是 U+2018（UTF-8 字节 `e2 80 98`），不是 ASCII `'`。固件逐字节匹配 SSID，写错一个字节 = `NO_AP_FOUND`。改动后用 `hexdump -C sdkconfig.local` 验证。切回热点时从 ZKY 改 SSID/密码即可（字节已验证过，历史记录在 `开发经验.md:249`）。
3. **esp-tls 全局 CA store**：IDF 5.5.3 的 esp-tls 只认 `cfg->cacert_buf`（`cacert_pem_buf` 是 union 别名），且 transport 的 `esp_transport_ssl_set_cert_data` 内部会 `len+1`。本会话试过 global store 方案又回退到 per-connection cert_pem（HTTP 路径验证过的），当前代码用 per-connection。
4. **mbedtls 调试**：`sdkconfig.local` 加 `CONFIG_MBEDTLS_DEBUG=y` + `CONFIG_LOG_DEFAULT_LEVEL_DEBUG=y` 可看到握手全流程（包括服务器证书链 dump——本会话靠它发现 4 证书链）。注意：debug 全开时 UART 115200 可能丢行，串口读取循环要紧凑。会话结束已把这两个调试开关从 sdkconfig.local 移除。
5. **serial 口会消失**：`Device not configured` 时重新 `ls /dev/cu.usb*`，一般插拔/等待即恢复。
6. **历史文档/脚本路径**：归档文档（`docs/embedded-project-intake-*`、`开发经验.md`）故意保留 Clara 字样；`scripts/backend_api_probe.py`、`scripts/capture.py` 等活脚本已同步改名。旧卷路径 `/Volumes/ML/...` 的脚本已失效。
7. **git 状态**：改名+修复已暂存未提交。提交时注意 `sdkconfig.local`、`build/`、`managed_components/` 是 gitignored，不会进去。

### 第 2 步：定位 ~6KB 泄漏（核心任务）

对 HTTP 会话路径做堆追踪，二选一：

- **方案 A（推荐）**：开 `CONFIG_HEAP_TASK_TRACKING=y` + 用 `heap_caps_monitor_...`/`heap_trace_*`；更直接的做法是在 `clare_net.cpp` 的 `http_perform` 里对比 `esp_http_client_init` 前后、`esp_http_client_cleanup` 前后的 `heap_caps_get_free_size/largest_free_block`（现有 TEMP 日志已证明泄漏发生在 cleanup 之后），再用 `heap_caps_dump_all()` 或按 alloc 分组统计定位未释放块。
- **方案 B**：临时在 esp-tls/mbedtls 的 cleanup 函数（`esp_mbedtls_cleanup`、`esp_tls_conn_destroy`）加日志/插桩，确认哪些 free 没执行。

排查重点（按嫌疑排序）：
1. `esp_http_client_cleanup` 是否释放了 keep-alive 连接与 esp_tls 上下文（对照 IDF 源码 `esp_http_client_cleanup` 实现）
2. `esp_mbedtls_cleanup` 中 IN/OUT buffer、`cacert` 解析结构、`peer_cert` 的释放（注意我们设了 `CONFIG_MBEDTLS_SSL_KEEP_PEER_CERTIFICATE=n`）
3. `http_perform` 的错误分支是否全部走到 cleanup（目前看是，但要确认 perform 失败路径）
4. mbedtls 3.6.x + `MBEDTLS_SSL_KEEP_PEER_CERTIFICATE=n` 组合的已知 issue

**验收标准**：`HTTP after cleanup` 的 `largest8` 恢复到 ≥24000（与 init 前 25088 相当），free8 恢复到 ≥42000。
